# Участие в разработке IronCore

Спасибо за интерес к **IronCore**! Проект открыт для любого вклада: от исправления опечаток и рефакторинга до реализации физики, сетевых оптимизаций и графического клиента.

---

## Как начать

1. Сделайте форк (Fork) репозитория и клонируйте его локально.
2. Создайте отдельную ветку для вашей задачи от актуальной ветки `main`:
   ```bash
   git checkout -b feature/название-фичи
   ```
3. Убедитесь, что установлены зависимости (`clang`, `libenet-dev`, `pkg-config`, `make`).

---

## Архитектурные правила

Проект строго разделен на три независимых модуля:
* `common/` — сетевой протокол (`protocol.h`), общие типы и константы. **Не должен зависеть от логики клиента или сервера.**
* `server/` — авторитарный сервер. Вся критическая игровая логика (движение, баллистика, расчет повреждений, экономика и опыт экипажа) рассчитывается **только здесь**.
* `client/` — клиентская часть (ввод игрока, отрисовка, интерполяция).

**Важно:** При изменении структур в `common/protocol.h` обязательно обновите код как в `server/`, так и в `client/`, чтобы обе части компилировались без ошибок.

---

## Стандарты кода (Code Style)

* **Стандарт языка:** чистый `C17` (`-std=c17`). Использование C++ и нестандартных расширений компилятора не допускается.
* **Предупреждения компилятора:** код должен собираться без единого warning'а с флагами `-Wall -Wextra -Wpedantic`.
* **Форматирование:**
  * Отступы — **4 пробела** (без табуляции).
  * Имена структур и типов — `PascalCase` (например, `TankState`, `CrewProfile`).
  * Имена функций и переменных — `snake_case` (например, `update_physics`, `player_id`).
  * Константы и макросы — `UPPER_SNAKE_CASE` (например, `TICK_RATE`, `MAX_PLAYERS`).
* **Сетевые структуры:** Все структуры, передаваемые по сети, должны быть упакованы директивой `#pragma pack(push, 1)` и использовать типы фиксированной ширины (`uint8_t`, `uint32_t`, `int32_t`).

---

## Использование ИИ-ассистентов

В разработке проекта приветствуется использование ИИ-инструментов (LLM) для генерации идей, ревью и написания кода. Главное требование: перед отправкой Pull Request автор должен **лично проверить, скомпилировать и понимать** каждую строчку предлагаемого кода.

---

## Отправка Pull Request (PR)

1. Перед созданием PR выполните чистую пересборку обоих модулей:
   ```bash
   make -C server clean && make -C server
   make -C client clean && make -C client
   ```
2. Опишите в PR, **что** было сделано и **зачем** (если PR закрывает Issue, укажите его номер, например `Closes #1`).
3. Старайтесь делать небольшие, атомарные PR — один PR на одну конкретную фичу или исправление.
